# Доменная модель и время

## Приглашения, решения и отзыв доступа

Миграция 0007 добавляет `AccountInvitation`, `AccessRequest`, `AccountControl`, `GrantRevocation`, `AccessReceipt`. Invitation хранит метаданные, срок, SHA-256 кода и зашифрованную копию только для локальной доставки; при активации/отмене копия очищается. Активация создаёт UserAccount без RoleAssignment и без BrowserSession. Повторное использование кода невозможно. Состояния приглашения выводятся из срока/accepted_at/cancelled_at.

AccessRequest хранит получателя/инициатора, роль/область/период/основание и решение независимого руководителя: pending → approved/rejected/cancelled. Только approved добавляет RoleAssignment. Фактическое начало — max(запрошенное, момент решения), окончание исключается; конец обязателен, не далее 366 дней от текущего момента. Будущие/истёкшие назначения не дают текущего доступа. Технические и бизнес-роли разделены в новом процессе.

AccountControl — оптимистическая версия административных действий над пользователем. GrantRevocation — отдельный неизменяемый отзыв с автором/основанием/датой, исходный RoleAssignment сохраняется. Центральная политика исключает отзыв, действующий на запрошенный момент `at`, без подмены истории. AccessReceipt — неизменяемая квитанция идемпотентной команды. Обязательный security-аудит и побочные эффекты входят в общую транзакцию; advisory lock сериализует изменения идентичности и активацию. Эффективное изменение доступа завершает сессии. Таблицы прежних предметных данных миграция не изменяет.

## Отчёты и неизменяемые выпуски

Миграция 0006 добавляет `Report`, `ReportRevision`, `ReportEvent`, `ReportRelease`, `ReportReceipt`, не обновляя существующие строки. Report фиксирует предложение, автора, reviewer, область, адресатов, вид conclusion/extract и связь previous_id. Состояния: draft → in_review → reviewed → released; возврат даёт returned, сохранение — новую редакцию в draft. Проверка относится к конкретному номеру и хешу содержания; самоутверждение исключено.

ReportRevision хранит JSON содержания, снимок конкретной версии предложения/источников/разрешённых ответов и SHA-256. ReportRelease содержит обе бинарные выгрузки, SHA-256 каждого файла, immutable manifest с именами участников на дату выпуска, результатом рассмотрения и датой. ReportEvent — неизменяемая история; ReportReceipt — защита от повторного выполнения. UPDATE/DELETE четырёх журналов запрещены runtime-роли и триггерами; Report после released дополнительно запрещает UPDATE. Исправление создаёт новый Report с previous_id; у одной редакции выпуска один непосредственный преемник. Старый выпуск не переписывается.

Область выписки замыкается на одном разделе; свободные человеческие выводы проходят отдельную проверку допустимости адресатам. Снимок не изменяется после обновления документов или исполнения. Текущий реестр исполнения читает разрешённые записи предложения отдельно, без записи в ReportRelease. Root/владелец БД остаётся вне гарантий прикладной неизменяемости.

Этап 2 добавляет `DocumentRecord → DocumentOriginal → DocumentVersion → DocumentTextBlock/SourceAnchor → ExtractedFragment`. Оригинал с SHA-256, объявленными метаданными и bytes неизменяем; DocumentRecord.version управляет конкурентным добавлением редакций. DocumentJob — отдельное сохраняемое техническое состояние и queue outbox. SourceAnchor может остаться прежней ручной выдержкой (context=null) или ссылаться на точный substring извлечённого блока. Нормализованный текст не заменяет оригинальную цитату.

Официальный status, document_date, effective_from и технический processing status различаются. Неизвестный effective_from допускает null; старые даты не изменены. Upload не утверждает функцию и не создаёт назначение. Внешняя политика редакции по умолчанию prohibited; synthetic_allowed требует явного synthetic=true. Файлы bytea входят в PostgreSQL-backup вместе с редакциями и аудитом.

`Department → Position → StaffingSeat → Appointment ← Employee`. `UserAccount` существует отдельно от сотрудника. `RoleAssignment` не совпадает с должностью. Синтетический реестр — одна организация с иерархией пяти отделов.

`DocumentVersion → SourceAnchor → DocumentedFunction → FunctionAssignment`. Функция относится к отделу; исполнитель определяется только при наличии документальной привязки к должности и действующего назначения. Одно членство сотрудника в отделе не создаёт покрытие. Привязка только к отделу даёт «недостаточно данных», если нет документированного исполнителя.

Техническое время — UTC aware timestamp, отображение — IANA `DISPLAY_TIMEZONE=Asia/Almaty`. Кадровые периоды — календарные даты `[начало, конец)`. Например, прекращение 2026-10-28 означает отсутствие назначения с начала 28 октября. Последний рабочий день в такую модель вводится как следующая календарная дата; UI явно объясняет это.

Функция отдельно имеет жизненный цикл: ещё не действует / действует / упразднена. Покрытие: covered / uncovered / unknown / not_effective / abolished. Временное назначение требует даты конца; непересечение действует для всех назначений одной единицы. Оформленное временное занятие свободной единицы реализовано как `Appointment.kind=temporary`. Замещение занятой единицы при отпуске и несколько одновременных ставок — следующие расширения с отдельными правилами.

Кадровая команда блокирует строку единицы, проверяет expected_version, основание, права и допустимость периода. БД дополнительно проверяет daterange exclusion. Новое назначение или прекращение меняет проекцию; `OfficialPersonnelEvent` навсегда сохраняет before/after, исходный источник, автора, время и idempotency key. Исправление последней даты прекращения ссылается на исходное событие. Сдвиг даты, конфликтующий с заменой, отклоняется.

Интервалы покрытия выводятся детерминированно из границ назначений и закреплений. Исторические снимки расчёта сохраняются в официальных событиях. Будущая дата сразу видна при выборе «на дату», уведомление публикуется не раньше вступления события в силу. Перезапуск сохраняет outbox и будущие задания.

Не реализованы: Office, QualificationEvidence, AuditEngagement, ComparisonRun/Finding, Case/Message, ProposalVersion/Review/Decision/ImplementationAction, ReportSnapshot. Они добавляются с функциональностью этапов 2–4; фиктивных пустых таблиц для них нет.

Эта запись описывает исходную границу этапа 1. Реализованные дополнения этапов 2 и 3 перечислены ниже; глобальный справочник QualificationEvidence, AuditEngagement и выпуск ReportSnapshot остаются последующими расширениями.

## Дополнение модели этапа 2

Миграция 0004 аддитивно добавляет DocumentCorpus/CorpusMember/CorpusSource (неизменяемые редакции и anchors комплекта), ComparisonRun (две стороны, критерии, права инициатора, версии обработки и сверка реестра), ComparisonFinding (кандидаты с доказательствами), FindingReview (отдельные версии решений), SearchChunk/IndexReceipt (производный индекс с ключом модели). Эти восемь таблиц доступны app-роли только SELECT/INSERT, дополнительно защищены immutable trigger. AnalysisJob отдельно хранит изменяемую очередь/lease/попытки/статус. Исторические таблицы 0001–0003 не переписываются.

Комплекты и запуски не имеют destructive edit/delete API. Новое содержание означает новый комплект/запуск, новая оценка человека — новую FindingReview с expected_version. ComparisonFinding — кандидат документального анализа; это не OfficialPersonnelEvent, не изменение DocumentedFunction, не утверждённое предложение и не самостоятельный кейс этапа 3.

## Дополнение модели этапа 3

Аддитивная миграция 0005 создаёт шесть таблиц без переписывания прежних данных:

- `ChangeProposal` — владелец-аудитор, текущий номер модели, состояние, оптимистическая версия и timestamps.
- `ChangeVersion` — неизменяемые заголовок, дата проектной модели, причина редакции и автор; уникальный номер внутри кейса.
- `ChangeSection` — неизменяемая часть версии одного отдела. Items сохраняют тип изменения, точный объект, введённое «до/после», источники, требования к квалификации, предложенного человека и обоснование квалификации. Impacts фиксируют доступные факты реестра на дату создания модели.
- `ChangeEntry` — append-only отправка задания, общее сообщение, закрытая заметка, ответ согласующего, управленческое решение, план/факт исполнения, проверка, отмена или ограниченный повтор. Любая запись привязана к версии; сообщения и ответы также к отделу.
- `ChangeReceipt` — неизменяемая квитанция идемпотентной команды, связанная с пользователем и хешем маршрута/тела.
- `ChangeOutbox` — независимое изменяемое состояние доставки. Уникальность entry/recipient исключает дубли; published/delivered/read timestamps, attempts и безопасный error_code не изменяют содержание исторической записи.

App-role имеет SELECT/INSERT на четыре таблицы доказательств и дополнительный immutable trigger. Для proposal/outbox разрешены SELECT/INSERT/UPDATE; destructive API нет. Официальные Department, Position, StaffingSeat, FunctionAssignment, Appointment и их прежняя история не изменяются командами предложений.

### Машина состояний и полномочия

| Исходное состояние | Команда и автор | Результат |
|---|---|---|
| — | Auditor создаёт предложение в своих scopes | draft, версия 1 |
| draft / in_review / returned | Владелец явно направляет ещё не адресованным участникам | in_review; новая отправка и срок для каждого получателя |
| in_review / returned | Адресованный согласующий отвечает agree/reject/request_info | Ответ сохранён по версии; сам по себе не утверждает и не исполняет проект |
| in_review / returned | Адресованный согласующий отвечает return | returned |
| in_review / returned | Независимый manager всех разделов: approve | approved, только после всех актуальных согласий и с основаниями |
| in_review / returned | Тот же manager: return / reject / accept_risk | returned / rejected / risk_accepted; принятие риска не равно утверждению исполнения |
| draft / in_review / returned / rejected / approved / risk_accepted | Владелец создаёт содержательную редакцию | Новая неизменяемая версия, draft; прежние ответы сохранены и неприменимы |
| approved / planned / partially_executed | Адресованный HR регистрирует план действия | planned либо сохранение partially_executed при уже исполненной части |
| approved / planned / partially_executed | Адресованный HR подтверждает completed с основанием | partially_executed, либо executed после всех действий |
| executed | Владелец-аудитор, не исполнитель, подтверждает проверку | verified |
| Состояние до фактического исполнения, включая planned | Владелец отменяет с причиной | cancelled; документы/замечания/решения сохранены |

После начала исполнения заменить модель нельзя: последующее содержательное изменение оформляется отдельным предложением. Выполненное действие повторно завершить или вернуть в planned нельзя. Cancel не откатывает официальное событие. Общие сообщения закрыты в verified/cancelled; закрытые рабочие заметки остаются отдельными авторскими записями.

Доступ требует одновременно живой бизнес-роли соответствующего отдела и адресованной версии/раздела. Для автора действует его текущая auditor scope. Адресат подразделения не получает соседний раздел межотдельского предложения, даже когда у кейса общий ID. Manager должен быть адресован и иметь manager scope всех разделов; автор не может утвердить собственное предложение при совмещении ролей. Отзыв полномочий скрывает и ранее прочитанные данные, уведомления и результаты последующих запросов. Новая неотправленная редакция оставляет прежнему адресату только прежнюю разрешённую историю без команд.

### Проектная модель, квалификации и фактическое исполнение

Проект представляет явные before/after по объектам и дате; это не произвольное перетаскивание официального графа. Для документированной функции сохраняются количество доступных закреплений/действующих назначений и названия закреплённых должностей; для единицы — число действующих и будущих назначений. Общие предупреждения о потере исполнителя, противоречиях ответственности и документах сопровождают эти факты. Полного автоматического доказательства последствий или применимости правового основания здесь нет: человек проверяет модель.

QualificationEvidence пока не является общим кадровым справочником: требования, описанные квалификации, кандидат и ссылки на документальные источники записываются внутри неизменяемого item. Сервер требует источники при указании кандидата и ограничивает его тем же отделом. Данные служат обоснованию ограниченного предложения человека; подбор, оценка людей или назначение Gemini не выполняются.

План и завершение — разные `ChangeEntry` для item key. Завершение требует существующего approved/registered_excerpt источника с применимой датой, не может быть будущим или раньше даты модели. Temporary_substitution дополнительно требует зарегистрированное временное назначение именно на эту единицу, с тем же источником, датой и выбранным кандидатом; событие, заменённое исправлением, отвергается. Остальные виды допускают документальное подтверждение HR без автоматической мутации реестров функций/штата/иерархии; интерфейс и контракт явно сообщают эту границу.

Доменная команда, обязательный аудит по затронутым отделам, квитанция и outbox атомарны. Приватная заметка не попадает в departmental business audit; security audit содержит только минимальные метаданные без заметки. Доставка проверяет живые полномочия до публикации и перед обработкой, не несёт текста в RabbitMQ. До восьми автоматических попыток, затем до двух явно разрешённых ручных циклов; повтор команды не расходует новый цикл. Напоминания — только ручные: до трёх на адресата/версию/отдел с интервалом 24 часа; эскалация — одна выбранному manager для просроченного задания без ответа.

История и версии выдаются страницами; отдельная process_entries проекция сохраняет последние ответы/доставку/исполнение независимо от выбранной страницы обсуждения. Текущая реализация сначала формирует разрешённую проекцию для безопасных counts/search и затем режет страницу; при существенно больших объёмах нужны оптимизация запросов и нагрузочные замеры. Постоянная история при этом не усекается в БД.
