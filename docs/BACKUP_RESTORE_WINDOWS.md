# Резервное копирование и восстановление OrgProekt на Windows

Автоматическое резервное копирование **по умолчанию выключено для удобства знакомства с проектом**. Обычная установка не создаёт расписание. Описанные здесь ручные копии и ежедневное задание включаются владельцем по желанию; уже установленное ранее задание автоматически не отключается.

Все команды ниже выполняются в **PowerShell из папки проекта**. Они проверены на PowerShell 7.6.5. Нужен настроенный Docker Desktop с работающим основным стендом. Python, PostgreSQL и age используются из контейнеров. В примерах путь `C:\Projects\OrgProekt` замените своим путём к репозиторию.

## Что сохраняется

Одна копия включает все таблицы PostgreSQL: пользователей и хеши паролей, зашифрованные MFA и резервные коды, роли/сроки/отзывы, документы и оригиналы DOCX/PDF, предложения/обсуждения/согласования, выпуски отчётов с PDF/DOCX, историю, аудит, поиск и состояния заданий. `pg_dump` и контрольные хеши используют один экспортированный MVCC-снимок. Во время копирования сайт продолжает работать; изменения после начала снимка попадут в следующую копию.

Оригиналы и выгрузки сейчас находятся в PostgreSQL bytea, поэтому отдельной несогласованной файловой копии нет. Непустая папка `uploads` вызывает отказ: при добавлении внешнего файлового хранилища процедуру нужно расширить.

В зашифрованный архив входят точная `.env` и имеющиеся файлы `.local/demo-accounts.json`, `.local/workflow-accounts.json`, `.local/report-reviewer/workflow-accounts.json`, `.local/audit-seal.json`. Состав ограничен этим списком. Пароль приглашённого пользователя хранится в БД в виде хеша. При восстановлении возвращаются этот хеш и защищённые данные MFA.

Архив защищён **age/X25519**, отдельным случайным ключом. Хеши и manifest внутри архива проверяются после полной аутентификации ciphertext. На хост записываются только шифрованный `.tar.age` и квитанция `.receipt.json`. Открытый pg_dump/tar находятся в `/work` tmpfs одноразового контейнера. Копирование исходных данных выполняется read-only; новая запись об операции находится в операторской квитанции, исходный аудит не меняется.

## 1. Создание копии

```powershell
cd C:\Projects\OrgProekt
./scripts/backup.ps1 -KeyFile .local/backup-keys/orgproekt.agekey
```

**В этой рабочей папке ключ уже создан и проверен.** Повторяйте команду без `-CreateKey`. На новом стенде, где ключа ещё нет, первый запуск:

```powershell
./scripts/backup.ps1 -KeyFile .local/backup-keys/orgproekt.agekey -CreateKey
```

Инструмент собирается автоматически при отсутствии `orgproekt-backup:local`. Для обновления его кода добавьте `-BuildTools`. Работающие образы приложения не заменяются. Ключ никогда не перезаписывается: повторный `-CreateKey` с существующим файлом отказывает.

Успех — JSON с `operation: backup`, `result: verified`, именем архива, SHA-256, количеством таблиц/строк и временем. Это означает проверку расшифрования и всех файлов, но реальное восстановление проверяется отдельно следующим шагом. Файл `.partial` не считается резервной копией. При штатной ошибке он удаляется; при аварийном завершении оставшийся ciphertext не используйте.

Папки ключа и архивов должны быть разными. Скрипт ограничивает Windows DACL текущим пользователем, SYSTEM и локальными администраторами. Ключ/архивы/приватные данные исключены из Git и Docker build context. Не отправляйте их в чат или публичные репозитории.

### Ежедневное расписание на этом Windows-компьютере

Задание **OrgProekt-Backup** установлено **ежедневно в 03:00 по местному времени Windows**. Оно запускается от текущего пользователя без сохранения его пароля, когда пользователь вошёл в систему. Требуются включённый компьютер и работающий Docker Desktop с основным OrgProekt. При недоступном Docker запуск фиксируется как `failed`; уже созданные архивы и ключ не удаляются. Пропущенный запуск может выполниться позже при доступности Windows, но регулярность проверяйте по статусу.

Проверить время следующего запуска и результат последней копии **без запуска сценария** (Windows PowerShell, папка проекта):

```powershell
cd C:\Projects\OrgProekt
Get-ScheduledTaskInfo -TaskName OrgProekt-Backup | Select-Object NextRunTime,LastTaskResult
Get-Content .local\backup-operations\daily-status.json
```

`LastTaskResult: 0` и `"result":"verified"` означают успех. Имя последнего архива и SHA-256 записаны в `.local/backup-operations/daily-status.json`; там нет паролей и ключей. Эти команды работают и при отключённом выполнении `.ps1`; менять системную политику ради проверки не требуется. Если результат `failed`, проверьте Docker Desktop и создайте копию вручную в разрешённой среде PowerShell. Для ручной проверки именно задания используйте Планировщик заданий Windows → **Библиотека планировщика заданий** → **OrgProekt-Backup** → **Выполнить**, затем снова прочитайте статус. Не создавайте второе задание с тем же именем.

На другом Windows-компьютере это расписание не появляется из архива. После настройки приложения и ключа установите его из папки проекта командой `./scripts/backup-schedule.ps1 -Action Install -At 03:00 -DaysInterval 1`. Изменить интервал: `./scripts/backup-schedule.ps1 -Action Update -At 03:00 -DaysInterval 1`; снять задачу без удаления архивов — `./scripts/backup-schedule.ps1 -Action Remove`. Запуск **создаёт только локальную копию** в `backups/scheduled/`. После успешного создания новой копии сохраняются три последние завершённые пары архив+квитанция из этой папки; более старые пары удаляются. Ручные копии в `backups/`, ключ, USB и проверочные стенды не затрагиваются. Новые архивы и квитанции нужно переносить во внешнее защищённое хранилище, а ключ хранить отдельно. Автоматического копирования на USB и уведомлений об отказе нет.

## 2. Хранение и recovery-копия ключа

На этом компьютере созданы `backups/` и `.local/backup-keys/`. Это проверенный локальный механизм, **один диск не защищает от потери компьютера**. Владелец должен перенести:

- архив `.tar.age` и его квитанцию на отдельный защищённый носитель/хранилище;
- recovery-копию `.agekey` отдельно от архивов, с ограниченным доступом;
- доверенную запись SHA-256 вне папки, которую можно одновременно подменить с архивом.

После копирования сравните `Get-FileHash -Algorithm SHA256` с квитанцией. Ключ нужен для расшифрования всех старых копий, зашифрованных им; утраченный ключ восстановить нельзя. Внутренние MFA/AUDIT-ключи сохранены внутри защищённого архива, внешний age-ключ в архив не входит. При ротации внешнего ключа создайте новый файл `.agekey` с другим именем, выполните новую копию и восстановление; старый ключ храните, пока нужны старые архивы. Это не меняет действующие MFA и HMAC-ключи приложения.

age защищает архив от изменения/неверного ключа, но public-key encryption не удостоверяет автора нового архива. Восстанавливайте только собственные доверенные копии; PostgreSQL dump содержит исполняемые определения SQL. SHA-256 берите из ранее сохранённой доверенной квитанции, не от неизвестного отправителя рядом с архивом.

Физическое шифрование Windows/WSL/swap/дисков здесь не включается и не объявляется проверенным. После восстановления приватная папка и Docker volume содержат открытые рабочие данные, как основной стенд. Для реальных данных требуется отдельная настройка шифрования диска/тома и защиты ключей. Память, swap и снимки VM также могут содержать секреты.

## 3. Восстановление в отдельный стенд

Выберите последнюю проверенную копию. В локальной папке можно получить её квитанцию так:

```powershell
$receiptFile = Get-ChildItem -LiteralPath backups -Filter '*.receipt.json' |
    Sort-Object LastWriteTimeUtc -Descending | Select-Object -First 1
$copy = Get-Content -LiteralPath $receiptFile.FullName -Raw | ConvertFrom-Json
./scripts/restore-lab.ps1 -Archive (Join-Path backups $copy.file) `
    -KeyFile .local/backup-keys/orgproekt.agekey -ExpectedSha256 $copy.sha256
```

На другом компьютере используйте пути к перенесённым архиву/ключу и SHA-256 из доверенного каталога. Значение `-ExpectedSha256` обязательно. Порт 8082 должен быть свободен; параллельно поднимать несколько копий на нём не нужно.

Скрипт создаёт случайное имя `orgproekt-restore-<UTC>-<суффикс>`, новую внутреннюю сеть и новый volume. Файл `compose.restore.yml` самостоятельный — его нельзя объединять с основным `compose.yml`. Основная `.env`, основной volume и сеть не подключаются к восстановленному приложению. Новые пароли PostgreSQL генерируются только для копии; MFA/AUDIT-ключи, пароли людей и права сохраняются. Gemini выключен, его ключ в копию рабочего окружения не передаётся. Worker/scheduler/RabbitMQ не запускаются, внешнего выхода у сети нет.

Восстановление допускается только в пустую БД с отдельной серверной меткой `orgproekt.restore_id`. Флагов `--clean`, `DROP DATABASE` и восстановления поверх основного стенда нет. Повтор в непустую БД отказывает. Миграции и seed не запускаются: проверяется именно содержимое снимка с его версией схемы.

После `pg_restore --single-transaction --exit-on-error` сравниваются все строки/столбцы, определения схемы, ACL, владельцы, триггеры, ограничения, индексы, функции и последовательности. Узкая нормализация учитывает равнозначную перепись PostgreSQL CHECK с массивами строк; другие выражения сохраняют точное сравнение. Проверяются HMAC-цепочка аудита, расшифрование MFA и SHA-256 оригиналов/PDF/DOCX.

**Сначала проверяется полное совпадение, затем только в копии** завершаются перенесённые сессии, инвалидируются reset-токены и отменяются неактивированные приглашения. Пароли, настроенная MFA, её резервные коды и бизнес-права не меняются. В журнал копии добавляется `system.restore_isolated`. Поэтому после открытия нужен новый вход, а приглашения/reset-коды основного сайта на копии не применяются.

Успех — `operation: restore`, `result: verified`, `schema_and_privileges_match: true`, `file_digests_match: true`, `audit_valid: true`. Затем открывается `http://localhost:8082/`. JSON результата и исходный manifest находятся в напечатанной приватной папке `.local/restore-labs/<имя>/`.

## 4. Проверка через браузер

Открывайте 8082 **в отдельном профиле или приватном окне**. Cookie localhost не разделяются по номеру порта; обычная соседняя вкладка может затронуть вход на основном 8080.

1. Войдите под `auditor` с прежними паролем и MFA. Откройте организацию, документы, своё предложение и выпущенный отчёт. Скачайте PDF/DOCX, проверьте заголовок/содержание/историю.
2. В другой сессии войдите под `it`: должен быть только ИТ, без финансового отдела и чужих отчётов.
3. Под `access` проверьте список пользователей, сроки/отзывы назначений и историю. Отозванный доступ Елены должен остаться отозванным; новые разрешения сама копия не выдаёт.
4. Обновите страницы: данные должны сохраняться. Основной 8080 продолжает работать отдельно.

Для автоматической проверки текущего учебного набора существует дополнительная команда. Она требует уже настроенной MFA у `auditor`, `it`, `access` и прежних файлов их паролей. На основном сайте она ничего не настраивает:

```powershell
$lab = Get-ChildItem -LiteralPath .local/restore-labs -Directory |
    Sort-Object Name -Descending | Select-Object -First 1
./scripts/test-restore-lab.ps1 -PrivateDirectory $lab.FullName
```

Выполняйте её на свежей копии до ручного входа: она дополнительно проверяет отсутствие действующих перенесённых сессий. Факторы читаются только из копии в приватный временный `qa-accounts.json`; `finally` удаляет этот файл после теста. QR/пароли/коды не попадают в stdout, trace/video отключены. Снимки и обезличенный результат — в `<папка стенда>/qa/`. Если PowerShell был аварийно закрыт, удалите оставшийся `qa-accounts.json` именно этого стенда вручную. Резервные коды основного аккаунта тест не использует.

## 5. Остановка и повторное открытие

Сохраните путь к своему успешно восстановленному стенду:

```powershell
$lab = Get-ChildItem -LiteralPath .local/restore-labs -Directory |
    Sort-Object Name -Descending | Select-Object -First 1
./scripts/restore-lab-control.ps1 -PrivateDirectory $lab.FullName -Action Status
./scripts/restore-lab-control.ps1 -PrivateDirectory $lab.FullName -Action Stop
./scripts/restore-lab-control.ps1 -PrivateDirectory $lab.FullName -Action Start
```

Stop оставляет проверенный volume и приватную папку. Start открывает тот же стенд и не повторяет восстановление. После проверки лучше держать копию остановленной. Основной проект `orgproekt` эти команды не принимают.

Автоматически удаляются только старые завершённые пары в `backups/scheduled/` сверх трёх. Ручные архивы, ключи и volumes не удаляются. Для удаления только ненужного тестового volume сначала проверьте имя проекта по `restore.guard.json`; разрушительная команда — `docker compose --env-file <его restore.env> -p <его имя> -f compose.restore.yml down --volumes`, с `RESTORE_PRIVATE_DIR`, указывающим на его папку. **Никогда не применяйте её к `orgproekt`.** Папку с клонированными секретами удаляют отдельно только после остановки и проверки абсолютного пути. Не используйте общий `docker system prune --volumes`.

## 6. Потеря компьютера, совместимость и границы

Архив данных не содержит образы Docker и дерево исходников. Он фиксирует точные ID работавших backend/Caddy. Для переноса заранее сохраните соответствующие исходники/lock-файлы и образы либо обеспечьте их проверенное восстановление. При отсутствии нужного ID скрипт откажет; подмена его новым образом без проверки не предусмотрена. Для отдельного экспорта образов на защищённый носитель используйте Docker `image save --output <файл.tar>` с нужными образами; не применяйте бинарный вывод через PowerShell `>`/конвейер. Текущие секреты в образы не включены. Перенос на другую ОС/архитектуру, Ubuntu, потерю Docker Desktop и импорт такого набора образов в этой работе не испытывали.

Это стенд проверки восстановления и чтения, не автоматическое переключение рабочего сайта. Состояния заданий/outbox сохранены, но RabbitMQ-очереди не копируются и фоновые отправки в копии не возобновляются. Возобновление обработчиков и разбор зависших заданий при настоящей аварии требуют отдельного эксплуатационного прохода. Caddy development HTTP сохранён только на loopback; production TLS/VM/шифрованное хранилище остаются отдельными задачами.

Текущий лимит содержимого архива — 192 МиБ, /work tmpfs — 1 ГиБ. При росте нужны пересмотр хранения/лимита и повторное испытание на реальном объёме. Текущая база значительно меньше лимита; нагрузочный тест большой БД не выполнялся. Ежедневное локальное расписание включено с хранением трёх последних автоматических копий; внешнее хранение новых копий и уведомления об ошибке не автоматизированы. RPO — момент последнего успешного снимка; измеренное время локального восстановления не является обещанием RTO при полной потере машины.

Типовые отказы: неверный SHA — проверьте доверенную квитанцию; неверный/утраченный ключ — используйте recovery-копию, обхода нет; непустая/непомеченная БД — создайте новый стенд; порт 8082 занят — остановите прежнюю копию; сбой проверки — сервисы копии останавливаются, основной сайт не трогается. Диагностика не печатает исходные исключения с возможными секретами. Не публикуйте `.env`, приватные папки, дампы и полный вывод Docker inspect/config.

Первичные руководства: [PostgreSQL pg_dump 17](https://www.postgresql.org/docs/17/app-pgdump.html), [pg_restore 17](https://www.postgresql.org/docs/17/app-pgrestore.html), [age](https://github.com/FiloSottile/age), [Docker internal networks](https://docs.docker.com/reference/compose-file/networks/). Формат шифрования age используется готовым инструментом, собственный алгоритм не реализован.
