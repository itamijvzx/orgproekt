# OrgProekt v0.1.0 — первая публикация

Версия для локального знакомства с документальным анализом и процессом организационных изменений. Автор — Синельников Иван Евгеньевич; проект существенно разработан с помощью ИИ. Авторский код распространяется по MIT. Все демонстрационные люди и документы вымышлены.

Новая установка входит по личному паролю **без обязательной MFA**. Автоматическое резервирование **не включается**; его можно настроить отдельно. У существующей установки сохраняются `.env`, данные, права, факторы входа и ранее установленное расписание. [Режимы запуска](LOCAL_DEMO.md).

## Как познакомиться с проектом

1. Скачайте исходники этого выпуска и выполните [инструкцию Windows](SETUP_WINDOWS.md). Нужны Docker Desktop с WSL 2 и Git; первая сборка загружает зависимости и модель поиска. GitHub хранит исходный код, сам сайт запускается на вашем ПК.
2. Выполните `seed`, `expand-demo`, `workflow-demo` на пустой базе. Пароли первых пяти аккаунтов находятся в `.local/demo-accounts.json`; `demo_manager` и `demo_reviewer` — в `.local/workflow-accounts.json`. Пароли создаются заново для каждой установки и не поставляются с репозиторием.
3. Под `auditor` пройдите [учебный пример](DEMO_WALKTHROUGH.md): две редакции → сравнение цитат → поиск → предложение → отчёт. Для первого просмотра отведите около 30 минут; полный цикл с переключением ролей потребует больше времени.
4. Для согласования используйте [сценарий предложений](CHANGE_WORKFLOW.md): `auditor` создаёт и направляет, `it` и `hr` отвечают, `demo_manager` принимает решение, `hr` подтверждает исполнение, `auditor` проверяет его.
5. Под `demo_reviewer` проверьте и выпустите отчёт, скачайте оба формата. Под `finance` убедитесь, что материалы ИТ недоступны. Отдельно можно пройти [приглашение и отзыв прав](ACCESS_WORKFLOW.md) под `access` и `demo_manager`.

При повторном старте заполненной установки не запускайте `seed` и не удаляйте volumes. Обычный stop/start сохраняет данные. Тег `v0.1.0` фиксирует этот выпуск; последующие изменения в `main` не изменяют его исходники.

## Ограничения и дальнейшие задачи

- **Только локальное знакомство с вымышленными данными.** Production намеренно заблокирован. TLS внутренних компонентов, размещение для реальной компании и перенос действующей установки в Ubuntu VM требуют отдельной реализации и приёмки. CI на Ubuntu не заменяет проверку VM.
- **Gemini выключен, ключ не требуется.** Подготовлен адаптер, но полного управляемого процесса LangGraph и приёмки живого Gemini нет. Сравнение и поиск работают локально; OCR для сканов не реализован.
- **Решения принимает человек.** Сходство текста и автоматический кандидат не доказывают противоречие, дублирование или отсутствие функции. Утверждение предложения не меняет автоматически все реестры и не подтверждает фактическую работу сотрудника.
- **Внешняя доставка не подключена.** Уведомления и обсуждения работают внутри приложения; приглашение передаётся вручную. Почта, корпоративный SSO и централизованное восстановление всех утраченных факторов не заявлены.
- **Проверки не означают отсутствие уязвимостей.** CI блокирует HIGH/CRITICAL с доступным исправлением по правилам проекта; оставшиеся находки и точные временные исключения опубликованы в [отчёте безопасности](DEPENDENCY_REVIEW_2026-11-11.md). Это не независимый аудит или сертификация.
- **Нет обещания количества одновременных пользователей.** Есть [измерения на одном ПК](LOAD_TEST_WINDOWS.md); документы, поиск, число процессов, CPU/RAM и диск влияют на результат. Нагрузка конкретной компании требует отдельного испытания.

Выпуск завершает согласованный учебный объём v0.1.0. Он не закрывает весь `MASTER_PROMPT_ORGPROEKT.txt`; дальнейшие функции и промышленная эксплуатация планируются отдельно.
