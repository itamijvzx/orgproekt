# Отчёты по предложениям — этап 4

В локальном учебном режиме (`LOCAL_DEMO_MODE=true`) вход выполняется без MFA. В шагах ниже пропускайте настройку и ввод второго фактора; при повторном подтверждении нужен только пароль. Права и согласования сохраняются. [Подробнее о режимах](LOCAL_DEMO.md).

Откройте **«Изменения» → «Отчёты»**. На телефоне пункт **«Отчёты»** находится в общем меню. Работа выполняется локально, без Gemini. Отчёт не изменяет структуру, назначения или функции.

## Кто участвует

- `auditor` готовит заключение из собственного предложения и сохраняет редакции.
- Отдельный `reviewer` проверяет содержание и выпускает отчёт. `demo_manager` остаётся руководителем согласования предложения: эта роль сама по себе не даёт права выпуска аудиторского заключения.
- Явно выбранные адресаты видят только выпущенный отчёт и только пока имеют доступ ко всем его отделам. Для ИТ в межотдельском предложении создайте отдельную выписку по ИТ.
- Право получить отчёт не даёт дополнительных прав на предложение. Источники открываются по прежним правилам доступа. Исторические черновики доступны только автору и назначенному рецензенту с действующими соответствующими ролями.

Для локальной демонстрации предусмотрен `demo_reviewer` — Ирина Клёнова. При установке по README его пароль создаётся в `.local/workflow-accounts.json`. При первом входе подключите MFA и сохраните резервные коды. На прежних установках, где рецензента создавали отдельно с `--output /private/report-reviewer`, пароль хранится в `.local/report-reviewer/workflow-accounts.json`.

Если рецензент ещё не создан, оператор может добавить его отдельно:

```powershell
./scripts/docker.ps1 compose -p orgproekt -f compose.yml --profile tools run --rm --no-deps tools python -m app.cli workflow-demo --username demo_reviewer --output /private/report-reviewer
```

Команда допускается только в development после учебного seed. Она откажет, если аккаунт или файл уже существуют; прежние учётные записи, пароли, MFA и роли не заменяются. Создавать рецензента повторно на текущем стенде не нужно.

## Пошаговая проверка

1. Войдите как `auditor`. Откройте «Изменения → Отчёты», нажмите **«Подготовить отчёт»**.
2. Выберите предложение, которое вы проверяли ранее. Для общего заключения оставьте **«Итоговое заключение по всем разделам»**. Для получателя одного отдела выберите **«Выписка: …»**; отдел должен входить в предложение.
3. Выберите Ирину Клёнову рецензентом. В адресатах общего отчёта выберите, например, Марка Кедрова и Романа Берёзова. Льва Соснова выбирайте только для отчёта, содержащего исключительно ИТ. Нажмите **«Создать черновик отчёта»**.
4. Проверьте блок **«Зафиксированные источники и позиции сторон»**. Сохраняется именно текущая на момент подготовки версия предложения с её источниками и разрешёнными ответами. Личные заметки не включаются. Снимок не обновляется при сохранении текста заключения.
5. Заполните все разделы. Пример для проверки документирования резервных копий:

| Поле | Пример содержания |
|---|---|
| Название | Заключение по документированию проверки резервных копий |
| Цель | Оценить документальное закрепление проверки восстановления резервных копий. |
| Область | ИТ; порядок регистрации результата проверки. Для общего заключения перечислите все проверяемые отделы. |
| Период | 20–30 октября 2026 года |
| Критерии | Запись содержит дату, результат и ссылку на проверенный комплект. |
| Метод | Сопоставлены сохранённые источники, предложение и ответы участников. Gemini не использовался. |
| Ограничения | Учебные данные. Фактическое восстановление не тестировалось. |
| Замечания и доказательства | Опишите конкретное расхождение и укажите документ/редакцию/пункт из сохранённых оснований. Не копируйте вывод этого примера, если ваше предложение о другом. |
| Значимость | Средняя: отсутствие ссылки затрудняет повторное подтверждение результата. |
| Рекомендации | Дополнить форму журнала и проверить полноту записей. |
| Мероприятия ответственные и сроки | Руководитель ИТ — подготовить форму до 15.11.2026; аудитор — проверить основание исполнения до 20.11.2026. |
| Профессиональный вывод | Укажите, что подтверждено, что остаётся открытым и на каких основаниях сделан вывод. |

6. Нажмите **«Сохранить редакцию»**, затем **«Направить на проверку»**. Пустые разделы сервер отклонит. Если сведений нет, явно опишите это как ограничение.
7. В другом профиле браузера войдите как `demo_reviewer`. Откройте «Изменения → Отчёты» и нужное заключение. Оно появляется у рецензента после направления, не на этапе авторского черновика.
8. Проверьте текст, источники и состав адресатов. Для проверки возврата выберите **«Вернуть на доработку»**, напишите комментарий и нажмите **«Сохранить проверку»**. Автор нажимает **«Обновить сведения»**, исправляет текст, сохраняет новую редакцию и вновь направляет отчёт. Прежние редакции доступны только для чтения в **«Сохранённые редакции»**.
9. Рецензент выбирает **«Проверено — готово к выпуску»**, пишет заключение, ставит отметку проверки источников, выводов и адресатов и нажимает **«Сохранить проверку»**. Если вход подтверждался более 10 минут назад, появится форма повторного подтверждения; после неё повторите действие.
10. Введите основание выпуска и нажмите **«Выпустить отчёт»**. Только теперь доступны **«Скачать PDF»** и **«Скачать DOCX»**. Отсутствие согласия подразделения со всеми выводами не блокирует выпуск: несогласие нужно отразить в заключении.
11. Войдите выбранным адресатом. Проверьте доступ к выпущенному отчёту и файлам, обновите страницу. Чужой отдел не должен видеть отчёт в поиске или открывать его по прямому API-запросу. Адресат не получает доступ к прежним черновикам.
12. У автора откройте **«Текущее исполнение — отдельно от выпуска»** → **«Загрузить текущий реестр исполнения»**. Новые разрешённые записи исполнения отображаются здесь; PDF/DOCX остаются прежними. Если пользователь не приглашён в предложение, этот реестр для него недоступен.
13. Для исправления выпущенного текста автор нажимает **«Подготовить исправленный выпуск»**, подтверждает рецензента и адресатов, заполняет новый черновик и вновь проходит проверку. Старый выпуск остаётся доступным. У одного выпуска допускается один непосредственный преемник; последующие исправления начинаются с последнего выпущенного отчёта.

## Что фиксируется и где границы

Каждое сохранение добавляет неизменяемую редакцию текста и ссылку на тот же зафиксированный набор доказательств. Выпуск сохраняет оба файла, хеши, дату, автора, рецензента, его заключение, основание выпуска и адресатов. Скачивание записывается в журнал. Повтор неизменённой команды не создаёт второй выпуск; устаревшая версия возвращает конфликт, введённый текст остаётся в форме.

Для выписки автоматически исключаются чужие разделы, общие межотдельские сообщения/решения и личные заметки. Рецензент дополнительно проверяет свободный текст автора: система не умеет автоматически распознавать упоминание чужого отдела в произвольно написанном выводе. Закрытые кадровые поля и обоснования квалификации кандидатов не включаются автоматически.

Скачанный DOCX можно изменить на компьютере получателя; это не изменит сохранённый выпуск. Для подтверждения совпадения используйте контрольные суммы исходных файлов. Электронная подпись, DRM, отзыв уже скачанной копии и защита от администратора БД/root не заявляются.

Очередь рецензента — список отчётов с фильтром «На проверке». Отдельная автоматическая рассылка уведомлений о стадиях отчёта пока не реализована. При отзыве полномочий рецензента или адресата выпуск блокируется; замена состава выполняется подготовкой нового отчёта, а не редактированием выпущенного. Большие отчёты ограничены 1000 блоками / примерно 1 млн символов доказательств. Нагрузочные испытания, полная инфраструктурная часть этапа 4 и живой Gemini остаются отдельной работой.
