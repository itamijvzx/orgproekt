# Перенос Windows → Ubuntu и резервирование

Пока проверен только локальный запуск и сохранение Docker volumes. Перенос существующей базы, шифрованный backup и restore drill **не реализованы и не считаются пройденными**. Этот документ отделяет доступный новый стенд от плана полноценной миграции.

## Новый синтетический стенд без переноса истории

1. Передать исходники и lock-файлы в VM без секретов и локальных каталогов, либо клонировать после отдельно разрешённой публикации репозитория.
2. Выполнить [DEPLOY_UBUNTU.md](DEPLOY_UBUNTU.md), создавая новые секреты и пустые volumes.
3. Выполнить seed один раз, получить новые личные пароли, настроить новый MFA. Старые аккаунты, сессии и история на этот стенд не переносятся.
4. Пройти сценарий README и проверить `api/health`. Существующий Windows volume сохранить до явного решения владельца об удалении.

## Перенос существующей истории — обязательный следующий этап

Потребуется отдельный проверенный инструмент, который:

* останавливает изменяющие API/worker операции на согласованное окно, фиксирует версию кода и миграций;
* создаёт согласованный PostgreSQL custom-format dump, сразу шифрует его, считает SHA-256 шифротекста; пароль не передаёт в аргументах shell;
* переносит ключи MFA и аудита через отдельный защищённый канал: новая случайная генерация этих ключей лишит возможности расшифровать существующий MFA и проверить историю;
* восстанавливает dump **в отдельную новую БД/volume**, создаёт минимальную runtime-роль, проверяет схему, число сущностей, интервалы, HMAC-цепочку и внешнюю контрольную точку;
* отзывает существующие browser sessions и recovery tokens, исключает ненужные тестовые секреты;
* поднимает outbox в новой очереди: задача содержит ID, незавершённые записи повторно доставляются с защитой от дублей; содержимое Docker volume RabbitMQ вручную не копируется;
* проверяет MFA, чужой отдел, события/историю и последующий restore drill до переключения origin;
* сохраняет старую систему для согласованного rollback без параллельной записи в две базы.

Прямое копирование Windows/WSL PostgreSQL volume в Linux не используется как план миграции. Изменение секретов БД в `.env` не изменяет пароль уже существующей PostgreSQL-роли.

## Что доступно сейчас для аудита

**PowerShell, Windows:**

```powershell
./scripts/docker.ps1 compose --profile tools run --rm tools python -m app.cli verify-audit
./scripts/docker.ps1 compose --profile tools run --rm tools python -m app.cli seal-audit
```

`seal-audit` сохраняет контрольную точку в `.local/audit-seal.json`. Защищённую копию нужно хранить отдельно от БД; это **не резервная копия**. Текущая сверка выявляет повреждение цепочки и удаление хвоста относительно сохранённого количества записей. Она не обеспечивает защиту от администратора, владеющего одновременно БД, HMAC-ключом и контрольной точкой.

Критерий будущего закрытия задачи: автоматическая команда backup → зашифрованный артефакт → restore в независимый volume → проверка данных/доступа/цепочки → зафиксированный отчёт и время восстановления. До этого не загружать реальные документы и не обещать восстановимость production.
