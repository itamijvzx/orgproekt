# Доступ: приглашения и назначения ролей

В локальном учебном режиме (`LOCAL_DEMO_MODE=true`) вход выполняется без MFA. В шагах ниже пропускайте настройку и ввод второго фактора; при повторном подтверждении нужен только пароль. Права и согласования сохраняются. [Подробнее о режимах](LOCAL_DEMO.md).

Раздел продолжает этап 4. При входе под существующим `access` (Дана Полевая) открывается **«Доступ»**. Здесь четыре вкладки: **«Пользователи»**, **«Приглашения»**, **«Назначения на подтверждении»**, **«История доступа»**. Сохранены прежний пароль, MFA и область администратора. Пароль исходного аккаунта находится только в локальном `.local/demo-accounts.json`.

Администратор управляет техническим доступом, а не содержанием документов и кадровых карточек. Новый пользователь самостоятельно задаёт пароль и подключает MFA. Приглашение само по себе не выдаёт доступ к подразделению. Назначение подтверждает другой уполномоченный `manager` в требуемой области. На основном учебном стенде для этого подходит уже существующий `demo_manager` — Роман Берёзов.

## Проверка приглашения

1. Войдите под `access`. Если MFA ещё не подключена, выполните обычную первоначальную настройку и сохраните резервные коды.
2. Нажмите **«Пригласить пользователя»** и заполните:

| Поле | Учебный пример |
|---|---|
| Логин нового пользователя | `training_it_01` — свободный личный логин латиницей; допускаются цифры, `_`, `.`, `-` |
| Имя пользователя | Елена Береговая · учебный представитель ИТ |
| Основание приглашения | Учебное приглашение для проверки доступа представителя ИТ. |
| Срок приглашения | 24 часа |

3. Нажмите **«Создать приглашение»**. Откроется вкладка **«Приглашения»**, состояние — **«Ожидает подтверждения»**. Новый аккаунт пока не создан.
4. В строке приглашения нажмите **«Получить код приглашения»**. После свежего подтверждения входа доступен код и срок. В текущем development-стенде это локальная учебная доставка: копируйте код вручную, внешняя почта не отправляется. Закройте окно кода перед снимком экрана.
5. Откройте отдельный профиль/приватное окно браузера. На странице входа нажмите **«У меня есть приглашение»**, вставьте код и задайте собственный пароль от 14 символов. Нажмите **«Создать личную учётную запись»**.
6. Войдите с новым логином/паролем, подключите MFA, сохраните резервные коды. Откроется «Моё пространство» с сообщением, что права на подразделение пока не назначены. В приглашении появится состояние **«Активировано»**, в списке пользователей — новая запись.

Повторное использование, отменённый/просроченный код и приглашение от администратора с отозванными полномочиями не активируются. Код не находится в адресе страницы, списках, localStorage или техническом журнале. Служебная копия кода хранится зашифрованной и очищается при активации/отмене; хеш остаётся для проверки. До завершения срока действующий код можно повторно получить после fresh reauth — например, при потере сетевого ответа. Для отмены нажмите **«Отменить приглашение»**, укажите причину и подтвердите. Для нового кода после отмены создайте новое приглашение с тем же ещё свободным логином.

## Назначение и подтверждение прав

1. Под `access` откройте **«Пользователи»**, найдите `training_it_01`, нажмите имя пользователя.
2. Нажмите **«Запросить назначение роли»**:

| Поле | Что выбрать |
|---|---|
| Роль | Представитель отдела |
| Область доступа | Информационные технологии |
| Начало действия | Текущая дата и время |
| Окончание действия | Например, через 30 дней |
| Основание назначения | Учебный доступ к сведениям ИТ на ограниченный срок. Доступ к другим отделам не предоставляется. |

3. Нажмите **«Направить на подтверждение»**. Запрос появится во вкладке **«Назначения на подтверждении»**, но бизнес-доступ ещё не появится.
4. В отдельной сессии войдите под `demo_manager`. Откройте **«Ещё» → «Доступ»** (на телефоне — общий пункт «Доступ»). По умолчанию показаны ожидающие запросы в области руководителя.
5. Нажмите имя нового пользователя. Проверьте получателя, роль, отдел, период, инициатора и основание. Выберите **«Подтвердить назначение»**, заполните **«Обоснование решения»**, например: «Личность учебного получателя, необходимость роли, отдел и срок проверены». Поставьте отметку проверки и нажмите **«Сохранить решение по правам»**.
6. Текущие сессии получателя завершатся. Войдите новым пользователем заново: он должен видеть только ИТ. Прямые API-запросы к документам/функциям/обзору другого отдела возвращают 404. Публичный UUID или участие в предложении не расширяют область.

Руководитель может отклонить запрос с основанием. Администратор может отменить ожидающий запрос. Автор запроса и получатель роли не могут подтвердить это назначение, даже при совмещении ролей. Если подходящего независимого руководителя нет, запрос остаётся без назначения; обхода подтверждения нет. Для учебного bootstrap руководителя используется прежний контролируемый `workflow-demo`, который добавляет только отдельный фиксированный аккаунт, без изменения существующих пользователей.

Новые назначения имеют явное окончание не далее одного года. Если запрошенное начало уже прошло, фактическое начало — момент подтверждения. Начало включается в период, окончание исключается. Будущая роль не работает раньше срока, истёкшая — не работает после окончания.

## Отзыв, блокировка и сессии

- В карточке пользователя рядом с действующей/будущей ролью нажмите **«Отозвать»**, укажите **«Основание действия»** и нажмите **«Подтвердить действие»**. Назначение станет **«Отозвано»**; исходная запись роли сохраняется, добавляется неизменяемый факт отзыва. Завершаются текущие сессии. После нового входа отозванная область недоступна, включая источники и ранее адресованные отчёты/выгрузки.
- Для изменения роли, отдела или периода отзовите прежнее назначение и оформите новое с отдельным подтверждением. Мгновенной подмены действующих прав нет.
- **«Заблокировать аккаунт»** прекращает возможность входа и завершает сессии. **«Разблокировать аккаунт»** возвращает возможность обычного входа, сохраняя пароль/MFA и оставшиеся действующие назначения. Прежние сессии не оживают, отозванные или истёкшие роли не восстанавливаются.
- **«Завершить все сессии»** требует основания и отзывает текущие входы без изменения пароля/MFA/ролей. Пользователь входит заново обычным способом.
- Собственный аккаунт администратор здесь не блокирует и назначения самому себе не выдаёт/не отзывает. Свои сессии и MFA управляются через «Моё пространство».

Для чувствительных действий требуется вход, подтверждённый не более 10 минут назад. При необходимости появится встроенная форма повторного подтверждения; после неё повторите исходное действие. При конфликте версии обновите сведения и проверьте сохранённый ввод. Повтор неизменённой команды использует прежний ключ, не создаёт повторного назначения/события.

## Администраторы и первоначальный доступ

Первоначальный `access` создан прежним одноразовым синтетическим seed оператором хоста. На существующей базе seed повторять не нужно. Учётная запись личная, со случайным паролем и обязательной MFA; общих паролей admin/admin нет. Данные этого пользователя миграция 0007 не меняет.

Для дополнительного администратора пригласите **отдельную личную учётную запись без бизнес-ролей**. В запросе выберите «Администратор доступа». Подразделение не назначается; подтверждение требует независимого manager с областью всех текущих подразделений организации. Административные и бизнес-роли в обычном процессе оформляются разным личным аккаунтам. Существующие исторические назначения не переписываются.

Оператор хоста/DB root остаётся сильнее прикладных ограничений. При отсутствии независимого руководителя/утрате всех факторов нужен документированный операторский процесс; публичной команды обхода MFA нет.

## Границы этого среза

Приглашения проверены в локальном development с ручной передачей кода. SMTP, проверка владения почтовым адресом и production-доставка не подключены. Полная административная процедура восстановления потерянной MFA остаётся отдельной работой; существующие личные резервные коды, замена фактора и операторский сброс пароля сохранены. Администратор не получает возможность устанавливать чужой пароль или выключать MFA.

Очередь подтверждения — вкладка запросов; отдельная автоматическая рассылка руководителям не реализована. Получатель получает минимальное уведомление об изменении доступа/сессий; подробности остаются в защищённой истории. Нагрузочный тест большого каталога пользователей не выполнен. TLS компонентов, зашифрованное хранилище и backup/restore остаются следующими частями этапа 4. Gemini не используется.
