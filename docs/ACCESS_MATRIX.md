# Доступ и роли

## Приглашения и управление правами — этап 4, 30.10.2026

| Действие | Полномочие и ограничение |
|---|---|
| Каталог пользователей/MFA-статус, приглашения, история | Текущий access_admin. Только технические сведения; пароли, MFA-секреты и recovery-коды не выдаются |
| Получение кода приглашения | access_admin + fresh reauth; только development/test, отдельное журналируемое действие; токен не включён в списки |
| Активация | Действующий одноразовый код и собственный пароль; роли и авторизованная сессия не создаются, затем обычный вход/MFA |
| Запрос роли | access_admin для другого пользователя, роль + отдел + конечный срок + основание. Не даёт немедленных прав |
| Подтверждение/отклонение | Независимый manager с текущей областью запрошенного отдела; ни инициатор, ни получатель не могут подтвердить. Технический access_admin требует manager во всех текущих отделах |
| Отзыв/блокировка/разблокировка/завершение сессий | access_admin для другого аккаунта + fresh reauth + основание + версия; собственный аккаунт управляется через «Моё пространство» |

Новый процесс не совмещает технический и бизнес-доступ в одном аккаунте; старые исторические назначения не переписываются. Все изменения ролей/блокировки завершают сессии получателя. Разблокировка не меняет пароль/MFA и не возвращает отозванные/истёкшие роли. Центральный `access.grants()` учитывает неизменяемый отзыв, поэтому прежние документы, очередь, поиск, отчёты и выгрузки не сохраняют доступ по старому назначению. Адресность отчёта или членство в предложении не расширяют scope. Bootstrap первого `access` остаётся контролируемым seed на пустой development-базе. Инструкция: [ACCESS_WORKFLOW.md](ACCESS_WORKFLOW.md). Начальная матрица этапов 0–1 ниже сохраняется как исторический срез.

## Отчёты — этап 4

| Действие | Условие |
|---|---|
| Подготовка, сохранение, направление | Владелец предложения с auditor во всех его отделах. Выбор выписки не обходит права автора на исходное предложение |
| Черновик и предыдущие редакции | Автор; назначенный reviewer после направления с актуальной ролью/областью. Выпущенный отчёт не открывает адресатам прежние черновики |
| Проверка и выпуск | Назначенный reviewer во всех отделах отчёта, отдельный от автора, fresh reauth, рассмотренная текущая редакция. Manager сам по себе не выпускает заключение |
| Получение PDF/DOCX | После выпуска — автор/назначенный reviewer/явно указанный адресат; действующий аккаунт и доступ ко всей области проверяются на каждом запросе |
| Ограниченная выписка | Отдельный снимок одного отдела, отдельная проверка и выпуск. Чужие и общие межотдельские тексты исключены; свободные выводы проверяет человек |
| Текущее исполнение | Доступ к отчёту плюс прежние правила адресного участия в предложении; отдельная текущая проекция |
| Исправление | Автор с актуальными правами создаёт новый отчёт с previous_id; прежний выпуск неизменяем |

При реализации отчётов на основном учебном стенде был добавлен только `demo_reviewer` (reviewer в пяти отделах); прежние роли `auditor`, `hr`, `it`, `finance`, `access`, `demo_manager` не менялись. Администратор доступа автоматически не видит отчёты. Текущий процесс приглашений и подтверждения новых назначений описан выше; локальные bootstrap-команды отделены от него.

## Базовый срез 0–1

Каждый запрос проверяет действующую серверную сессию, MFA, активность аккаунта и актуальные назначения ролей. Scope — явный список отделов, сроки `[valid_from,valid_until)`. `null` scope не открывает организацию.

| Операция | auditor | hr | department | access_admin |
|---|---|---|---|---|
| Граф, функции, источники, публичные назначения | В назначенных отделах | В назначенных отделах | В назначенном отделе | Нет |
| Кадровое событие | Нет | В scope + повторный вход не старше 10 минут | Нет в этом срезе | Нет |
| Табельный номер | Нет | В scope и явный запрос private | Нет | Нет |
| Бизнес-история | В scope | В scope | В scope | Нет |
| Журнал безопасности | Нет | Нет | Нет | Да, минимизированные атрибуты |
| Уведомления | Только свои и актуальный scope | Только свои | Только свои | Только свои |
| Сессии/резервные коды | Только свои | Только свои | Только свои | Только свои |
| Выдача бизнес-прав через API | Не реализована | Не реализована | Не реализована | Не реализована |

`reviewer` и `manager` участвуют в процессе этапа 3; бизнес-чтение требует scope. В seed совмещения ролей нет. Права не принимаются из произвольного JSON. Угадывание UUID возвращает одинаковый 404 для чужого и отсутствующего объекта. Публичная ошибка не раскрывает имя чужого отдела.

В очередь передаётся только ID outbox. Worker заново вычисляет аудиторов и активные права перед созданием уведомления. Чтение уведомления ещё раз проверяет права. При выходе клиент сбрасывает бизнес-данные из памяти; API отвечает no-store. Секреты и бизнес-кеш не сохраняются в localStorage.

Запланированный экспорт не имеет открытого обходного API. Его ACL проверяется при реализации, а не считается проверенным заранее. Владелец Windows/VM/DB root технически сильнее прикладного администратора.

## Предложения — этап 3

| Действие | Условие |
|---|---|
| Создать/изменить версию/направить/отменить | Автор-аудитор с текущей областью всех разделов; допустимое состояние |
| Читать предложение/историю | Авторство или адресное приглашение соответствующей версии плюс текущая бизнес-область; выдаются только разрешённые разделы |
| Общее сообщение | Участник разрешённого раздела текущей версии; источники того же отдела |
| Закрытая заметка | Только автор-аудитор; содержимое не появляется в общем обсуждении или уведомлении других лиц |
| Ответ согласующего | Адресованный department/hr/reviewer/auditor; автор не согласует собственную версию |
| Управленческое решение | Приглашённый manager во всех разделах, не автор, fresh reauth; для утверждения актуальные согласия всех необходимых адресатов |
| План/исполнение | Приглашённый HR по разделу, fresh reauth, утверждённая версия, официальное основание и проверка даты/события |
| Проверка исполнения | Автор-аудитор с полной областью, fresh reauth; все действия исполнены, автор не был исполнителем |
| Уведомление | Только адресат с актуальными правами; повторная проверка перед выдачей и доставкой |

Менеджерские решения по межотдельскому кейсу не открывают закрытые части участнику одного отдела. После новой редакции участник сохраняет чтение ранее адресованной истории, а новые данные получает после нового направления. Access_admin не получает бизнес-содержимое автоматически. Учебные роли добавляются отдельным контролируемым bootstrap без изменения прежних аккаунтов.

## Документы — этап 2

Чтение метаданных, редакций, текста, источников и скачивание: бизнес-роли только в действующей области отдела. Загрузка/новая редакция/повтор/отмена: auditor, hr, department, manager с явным scope; reviewer читает, access_admin автоматически не получает бизнес-доступ. Загрузка и повтор требуют свежего MFA/reauth. Права не передаются в multipart, очередь содержит только job_id. Worker проверяет аккаунт, исходную сессию и текущие назначения ролей до разбора и перед записью; при отзыве результат не публикуется. Старые назначения ролей и аккаунты миграция не изменяет.

Внешняя обработка по умолчанию запрещена. Подготовленный Gemini context loader дополнительно требует `synthetic=true`, `external_policy=synthetic_allowed` и job=ready; partial/сканы/ручные источники автоматически наружу не отправляются. Каждая попытка SDK и возврат результата вызывают loader повторно. Ни upload, ни worker не запускают SDK.

## Комплекты и поиск (этап 2)

- Чтение корпусов/сравнений/истории требует read для всех включённых редакций; частичный доступ не выдаёт частичный результат, название или счётчик. Администратор доступа без business-role не получает новые данные.
- Создание комплекта, сравнения и индекса — document.write во всех отделах. Отмена/повтор повторяют эту проверку и текущую MFA-сессию.
- Рассмотрение кандидата — auditor во всех отделах запуска; HR/manager/department могут создавать запуск, но не подтверждать его за аудитора. Решение не утверждает изменение официальных функций.
- Поиск ограничивает разрешённые SourceAnchor до FTS/cosine/RRF; отдел/комплект/редакция от клиента не предоставляют права. После inference проверяются отзыв сессии, активность пользователя и область.
- Снимок прав инициатора в ComparisonRun нужен для истории. Worker и каждый HTTP-запрос используют текущие полномочия, а не этот снимок. Локальная maintenance-команда доступна оператору контейнера и не создаёт HTTP-обхода прав.
